# Contributing to Tramline

Thanks for wanting to help! Tramline is young, and there's plenty to do whatever your background: code, design, docs, testing on unusual hardware, or telling us where the rough edges are.

## Ways to help

- **Try it and report what breaks.** Bug reports with steps to reproduce are gold. Open an issue.
- **Pick up a roadmap item.** [docs/roadmap.md](docs/roadmap.md) has the full plan. Phase 6 (multi-node, the adapter SDK and Proxmox) is where the next big work is.
- **Write a compute adapter.** Once the adapter SDK lands, each provider (Hetzner, AWS, GCP, Azure, …) is a self-contained package behind one interface.
- **Polish the UI.** The canvas, panels and settings are SvelteKit + shadcn-svelte, and small UX improvements are very welcome.
- **Improve the docs.** If something confused you, it will confuse the next person too.

For anything larger than a bug fix, please open an issue first so we can agree on the approach before you put time in.

**Security issues:** please don't open a public issue. See [SECURITY.md](SECURITY.md).

## Development setup

Requires Node 24 (see `.nvmrc`), pnpm 10, and a running Docker daemon (Docker Desktop, OrbStack or Colima).

```bash
nvm use
pnpm install
cp apps/web/.env.example apps/web/.env   # then set TRAMLINE_SECRET_KEY (openssl rand -base64 32)
pnpm dev
```

Open http://localhost:5173 and create an account. The SQLite database is created at `apps/web/data/tramline.db`, and migrations run automatically on start. `pnpm dev` also starts the local agent. Deployed services are served at `http://<service>-<id>.localhost` through the ingress on port 80 (set `TRAMLINE_INGRESS_PORT` to change it).

To deploy private repositories and redeploy on push, open **Settings → GitHub** and create the GitHub App (set `TRAMLINE_URL` first). GitHub sends push webhooks when the install is reachable over HTTPS; otherwise Tramline polls tracked branches every `TRAMLINE_GIT_POLL_SECONDS`.

| Command                                   | What it does                                  |
| ----------------------------------------- | --------------------------------------------- |
| `pnpm dev`                                | Start the web app on http://localhost:5173    |
| `pnpm check`                              | Type-check every workspace                    |
| `pnpm lint`                               | Prettier + ESLint/tsc                         |
| `pnpm test`                               | Unit, API and component tests                 |
| `pnpm test:coverage`                      | Same, with coverage gates (as CI runs it)     |
| `pnpm test:e2e`                           | Playwright against a production build         |
| `pnpm --filter @tramline/web db:generate` | Generate a migration after editing the schema |

To run the e2e tests that deploy real containers: `TRAMLINE_E2E_DOCKER=1 pnpm test:e2e`.

## Repository layout

```
apps/web/            SvelteKit app: UI, REST API (/api/v1), agent API (/api/agent/v1), control plane
apps/agent/          node agent: converges Docker to the desired state, runs the Caddy ingress
packages/contracts/  zod schemas shared by the API, client, CLI and agent
packages/client/     typed API client + resource definitions
packages/mcp/        MCP server for AI agents, built on the client
```

The architecture follows a desired-state model: the UI and API only change desired state in the database, and each node's agent converges Docker to match and reports back. [docs/roadmap.md](docs/roadmap.md#architecture) explains it in detail.

### The resource model

UI code never calls `fetch` directly. It goes through typed resources:

```ts
import { api } from '#lib/api.js';

const projects = await api(fetch).projects.getAll();
await api().projects.update(id, { name: 'Renamed' });
```

`packages/client` maps `getAll / get / create / update / remove` onto REST routes in `apps/web/src/routes/api/v1`. Those routes validate input with the `packages/contracts` schemas and call domain functions in `apps/web/src/lib/server/domain`. In components, `Collection` (`#lib/resources/collection.svelte.js`) wraps a resource with reactive, optimistic state.

To add a resource:

1. Add its schemas to `packages/contracts`.
2. Add `defineResource(...)` in `packages/client/src/resources` and register it in `createClient`.
3. Add domain functions in `apps/web/src/lib/server/domain`, plus a spec.
4. Add thin `+server.ts` handlers using `endpoint()` and `body()`.

The better-auth tables in `apps/web/src/lib/server/db/schema/auth.ts` are generated by `@better-auth/cli generate`. Regenerate them rather than editing by hand.

## Tests and CI

Every feature ships with tests: unit or API specs next to the code, and a Playwright e2e test for anything a user can see. Vitest reads `apps/web/.env.test` (an in-memory database and a throwaway secret). Coverage thresholds live in each workspace's Vitest config and should only ever go up.

CI runs on every pull request:

- **CI** (`.github/workflows/ci.yml`): lint and type-check, unit tests with coverage, and Playwright end-to-end tests that deploy real containers.
- **Security** (`.github/workflows/security.yml`): CodeQL, gitleaks secret scanning and `pnpm audit`.

Before opening a pull request, run:

```bash
pnpm lint && pnpm check && pnpm test
```

## Pull requests

- Keep each PR focused on one change, and describe what it does and why.
- Include tests, and update docs (including [SECURITY.md](SECURITY.md) if the change affects how secrets, containers or access are handled).
- Security is a first-class goal: the safe choice should be the default. If a change trades security for convenience, call that out in the PR.
