# Security

Security is a core goal of Tramline: it runs your code on your infrastructure and holds your secrets, so the safe choice should always be the default. See [Secure by default](docs/roadmap.md#secure-by-default) for the design and what is still to come.

## Reporting a vulnerability

Please **do not open a public issue**. Report it privately through GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) on this repository, with steps to reproduce and the affected version. We aim to acknowledge reports within 3 working days and to publish a fix and advisory as soon as one is ready.

## Supported versions

Tramline is pre-1.0. Only the latest `main` receives security fixes.

## What Tramline does today

- **Secrets:** variable values and deployment snapshots are encrypted at rest with AES-256-GCM, using a key derived from `TRAMLINE_SECRET_KEY`. Sealed variables are write-only: the API never returns them. Values of sealed and secret-looking variables (including a sealed value copied into another variable through references), and passwords inside URLs, are masked in deployment logs before they are stored. Masking prevents accidental disclosure; it cannot stop code that is given a secret from deliberately encoding and leaking it.
- **Containers:** every workload runs with `no-new-privileges` and all capabilities dropped except a small allowlist (no `NET_RAW`, `MKNOD`, `SYS_CHROOT`, …), a process limit, and an optional memory limit and read-only root filesystem. Workloads never get host mounts, so the Docker socket cannot leak into them.
- **Containment:** a workload can reach its own environment, the internet, DNS and published ports, and nothing else private. A firewall container on each node (host network, `NET_ADMIN` only, the agent's own image) keeps rules in Docker's `DOCKER-USER` chain and the host's `INPUT` chain. Those rules drop traffic from environment networks to the cloud metadata endpoints (`169.254.169.254`, and Azure's `168.63.129.16`), to every private range (the LAN, link-local, CGNAT, the mesh, other environments and Docker's other networks), and to the host's own ports (SSH, the agent, Tramline itself on the local node). Builds, which run a repository's own steps, lose the metadata endpoint too. A service can be allowed specific private ranges (a NAS, a database on the LAN), but never the metadata endpoint: those drops come first. The rules sit in Tramline's own chains, replaced atomically with `iptables-restore` in whichever backend Docker uses, and are put back within seconds if a reboot or firewall reload removes them. The Nodes page warns about any node where they can't be applied, such as Docker's nftables backend or `TRAMLINE_CONTAINMENT=off`. Docker's DNS only resolves names on a container's own networks, so another environment's `postgres` doesn't resolve. Workloads are given no platform credential (no agent, API or join token, no Docker socket), and nothing in Tramline trusts a request because of the address it comes from. Every blocked attempt is counted per container, by kind (metadata, private range, host), along with containers opening connections fast enough to be a scan. They show on the service's Metrics tab with a button to stop the deployment, and raise an alert. An end-to-end test checks all of this against real Docker.
- **Builds:** source builds run in a rootless BuildKit container, never `--privileged`. It does relax Docker's seccomp and AppArmor profiles for the builder only, which its user namespace requires. Service variables reach builds as BuildKit secrets, which BuildKit doesn't write into images or logs (a build step can still print or copy one). Build tools are pinned by checksum and re-verified on every use. Every build and image scan runs in a fresh builder of its own, removed afterwards, with BuildKit's process sandbox on, so build steps run in containers of their own and can't see the builder or any other job; build caches are kept per organization. Builds have memory and process limits and a deadline, and a build that is cancelled or times out is stopped, not just reported. (Disk use isn't limited yet.)
- **Images:** every image is scanned with Trivy before it runs, by default. Built images are scanned as a tarball before they reach Docker; registry images are scanned by the exact digest pulled, and the deployment then runs that digest. Per service, `warn` shows the findings and deploys, `block` refuses images with critical vulnerabilities that have a fix (and images that could not be scanned), and `off` skips the scan. Trivy runs inside the unprivileged builder, without access to the Docker socket, and is pinned by checksum.
- **Backups:** a dump or restore that fails anywhere in its pipeline is reported as failed, Postgres restores stop at the first SQL error, and retention never deletes the newest successful backups to keep failed ones. Encrypted on the node with a per-backup AES-256-GCM key (wrapped with `TRAMLINE_SECRET_KEY`) before upload, so the bucket provider only ever stores ciphertext. Nodes upload and download through presigned URLs for single objects and never hold bucket credentials; the bucket's secret key is encrypted at rest and write-only in the API. A restore applies nothing unless the whole backup authenticates, and restore drills prove backups can be restored before they are needed.
- **The control plane's database:** with `TRAMLINE_BACKUP_S3_*` set, it is snapshotted hourly, encrypted with a key derived from `TRAMLINE_SECRET_KEY` before upload, and drilled daily.
- **GitHub:** Tramline's GitHub App asks only for read access to repository contents and metadata. Its private key and webhook secret are encrypted at rest, and push webhooks are verified with HMAC in constant time. Installation tokens live for an hour, are never stored, are issued only for installations the organization connected, and are restricted to the one repository a build needs; they are only ever sent to `https://github.com`. Connecting an installation needs GitHub's user authorization: Tramline checks the person connecting it can access it on GitHub (their user token is used once and never stored), so knowing an installation's ID is not enough.
- **Custom domains:** traffic is routed only after a TXT record proves the domain is yours, hostnames are unique across the install, and generated names can't be claimed. HSTS on a custom domain covers that host only.
- **Data browser:** read-only by construction: the control plane builds every query, each runs in a `READ ONLY` transaction with a statement timeout inside the database container, and table names are checked against the database's own list.
- **API tokens:** shown once and stored as SHA-256 hashes; scoped (`read`, `write`, `deploy`), optionally expiring, and tied to their creator's membership. `write` only stages changes; applying them and deleting anything that runs needs `deploy`. Tokens cannot create tokens, change organization settings or manage nodes, and every change made through the API is recorded in the audit log.
- **Sign-in:** optional TOTP two-factor authentication with backup codes, and passkeys (WebAuthn) bound to the install's hostname.
- **CI without secrets:** GitHub Actions workflows from trusted repositories (pinned by repository id, optionally limited to refs and environments) exchange their OIDC token, verified against GitHub's keys with the issuer, audience and expiry checked, for an API token that lasts 15 minutes.
- **Nodes and agents:** agents connect outbound with per-node tokens (stored hashed) and need no inbound control port. A node's reports (containers, builds, logs, metrics, backup jobs) only count for work assigned to it. Machines join with one-time, expiring join tokens. Nodes are managed only by install admins, an explicit grant: the first admin claims the install with a one-time setup token from the server's data directory. Compute accounts (the credentials Tramline uses to create machines on Proxmox or a cloud) belong to the install too and are managed only by install admins, through a signed-in session, never an API token. Their credentials are encrypted at rest as a whole, and secret fields are write-only in the API. A machine an adapter creates gets its join token only through its cloud-init user data. For Proxmox, which can't take user data through its API, the VM fetches it from a seed URL with a random ID; the seed is stored encrypted and stops working once the VM enrolls or its token expires. Removing a node destroys its machine; if that fails the node is kept, so no machine is left running unseen. The Proxmox adapter always validates the certificate chain, expiry and hostname, accepts an explicit private CA, optionally pins the host's certificate fingerprint before sending the API token, and only destroys VMs it tagged `tramline`.
- **Metrics and alerts:** a service's metrics are only served to its organization; node metrics, like nodes, are visible to everyone on the install. Alerts can be posted to a webhook the operator sets with `TRAMLINE_ALERT_WEBHOOK_URL`; the request doesn't follow redirects, and its body holds the alert's message, which names the node or service.
- **Access logs:** every request to a service's public domains and every connection to its TCP proxy is logged by the node that took it (Caddy's access log, and a line per connection from the proxy), with the time, host, method, path, status, duration, size, user agent and the visitor's address. Only an organization's owners and admins see them, on the service's Traffic tab. The visitor's address is the connecting one, except from proxies Tramline trusts: Cloudflare's `CF-Connecting-IP` header is believed only on the tunnel's own listener and only from the host (service containers share networks with the ingress and could set it themselves), and `X-Forwarded-For` only from addresses in `TRAMLINE_TRUSTED_PROXIES`, read from the right. Each address's network is looked up in an offline table (iptoasn.com's by default, `TRAMLINE_ASN_DATA_URL`) downloaded weekly; addresses themselves are never sent anywhere. `Authorization` and cookies are never stored: Caddy redacts them and Tramline keeps only the user agent of a request's headers. Entries are kept for `TRAMLINE_ACCESS_LOG_DAYS` (14; 0 keeps none) within `TRAMLINE_ACCESS_LOG_MAX_ROWS`, successful requests on a busy service are sampled (past 300 a minute, one in ten is kept and counted for ten), and `TRAMLINE_ANONYMIZE_IPS=true` stores addresses without their last part. Nodes belong to the install, so a node's agent can report traffic for any service's domain, as it could already receive any service's secrets.
- **Web app:** a nonce-based Content Security Policy with no inline or eval scripts, `X-Frame-Options: DENY`, `nosniff`, a strict referrer policy, HSTS over HTTPS, rate-limited sign-in, and organization scoping on every query.
- **Ingress:** HTTPS with automatic certificates and HSTS on real domains. Caddy's admin API is never exposed.
- **Supply chain:** CodeQL, gitleaks secret scanning, `pnpm audit` and Dependabot run in CI.

## Operating a secure install

- Generate `TRAMLINE_SECRET_KEY` with `openssl rand -base64 32` and keep it out of the repository. Losing it makes stored secrets and backups unreadable; leaking it exposes them. Keep a copy somewhere other than the server.
- Serve the control plane over HTTPS (`TRAMLINE_URL=https://…`).
- Treat `apps/web/data/local-agent.token` like a password: it lets an agent receive your services' secrets. The same goes for `setup-token` in the data directory until someone claims the install, so claim it as soon as the install is up.
- Run one control-plane process. Events, live logs, pending data-browser queries and the schedulers live in that process's memory; several web workers would each run their own.
- Sign-up is by invitation once the install has an admin (`TRAMLINE_SIGNUP=invite`, the default): new accounts need an invite link from an organization's owner or admin. Set `TRAMLINE_SIGNUP=open` only if anyone who can reach the install should be able to create an account.
